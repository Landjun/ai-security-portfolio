# 智能合约漏洞:重入攻击 (Reentrancy)

> `08 区块链安全` 旗舰案例。最经典的智能合约漏洞,2016 年 The DAO 事件因此损失约 6000 万美元,直接导致以太坊硬分叉。

## 1. 原理

合约在**更新自身状态之前**就向外部地址转账(`call{value:}`)时,会把控制权交给外部合约。
攻击者在收款回调(`receive`/`fallback`)里**再次调用提款函数**——此时余额还没清零,
于是反复重入、把合约资金抽干。

## 2. 代码对照(审计参考)

```
reentrancy/
├── Vulnerable.sol   # 漏洞合约(先转账后清零)
├── Fixed.sol        # 修复合约(CEI + 重入锁)
└── README.md
```

对照阅读两份合约:`Vulnerable.sol` 在 `withdraw()` 里**先 `call{value:}` 转账、后清零余额**,
攻击者在 `receive` 回调里重入即可抽干;`Fixed.sol` 用**检查-生效-交互(CEI)顺序 + `nonReentrant` 重入锁**
堵住该路径。本模块只做**静态审计示例**,不部署、不执行攻击模拟。

## 3. 防护

1. **检查-生效-交互(CEI)**:先更新本合约状态(清零余额),再做外部调用。
2. **重入锁(ReentrancyGuard)**:`nonReentrant` 修饰符,从根上阻止重入。
3. **优先用 transfer/send 而非 call**(或限制 gas),减少回调能力(注意各有取舍)。
4. **拉模式提款**:让用户主动领取,降低复杂外部交互。

## 4. 修复建议
把所有"外部调用前未完成状态变更"的函数改为 CEI 顺序;对涉及资金的函数统一加 ReentrancyGuard;
用 OpenZeppelin 的成熟实现而非自造。

## 5. 审计检查清单
- [ ] 是否存在"外部 call 在状态更新之前"的函数?
- [ ] 涉及资金/关键状态的函数是否加了重入锁?
- [ ] 是否遵循检查-生效-交互顺序?
- [ ] 跨合约调用是否考虑了回调重入(包括只读重入)?

## 安全边界
Solidity 仅为审计教学示例,不编译部署、不执行、不针对任何真实合约;仅用于学习漏洞模式与防护写法。
