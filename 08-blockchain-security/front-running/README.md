# 智能合约漏洞:前置交易 / 抢跑 (Front-running / MEV)

## 1. 原理
以太坊交易先进入公开的 **mempool** 才被打包。攻击者(含搬运机器人、矿工/验证者)能看到
待打包交易的内容,用**更高 gas 抢先**执行(front-run)、夹在前后(sandwich)套利。
凡是"谁先提交谁得利"且**提交内容明文**的设计,都暴露在 MEV 下。

## 2. 代码对照
- [`Vulnerable.sol`](Vulnerable.sol):`claim(answer)` 明文提交答案进 mempool,会被抢跑夺奖。
- [`Fixed.sol`](Fixed.sol):**commit-reveal** 两阶段——先提交哈希承诺(绑定地址+盐),延迟后再揭示明文。

## 3. 审计要点(危险模式)
- "第一个提交正确值/最优价"的奖励逻辑,且**提交内容明文**。
- 价格/拍卖/清算缺少滑点保护或最小成交保护。
- 无 commit-reveal、无私有交易通道(如私有内存池)考量。

## 4. 修复建议
用 commit-reveal 隐藏意图;承诺里绑定 `msg.sender` + 随机盐防冒领;
交易加滑点/最小输出保护;必要时走私有 mempool(防夹子)。

## 5. 审计检查清单
- [ ] 是否存在"先到先得 + 明文提交"的可抢跑逻辑?
- [ ] 是否用 commit-reveal 隐藏敏感意图?
- [ ] 兑换/拍卖是否有滑点/最小成交保护?

## 6. 面试表达
> "抢跑的根源是交易先进公开 mempool 再打包,机器人看到你的明文交易就用更高 gas 插队。凡是'谁先提交谁得利'又明文的设计都危险。修复用 commit-reveal:先提交绑定地址和盐的哈希承诺,延迟后再揭示明文,抢跑者看不到内容也冒领不了;兑换类则加滑点保护。"

## 安全边界
Solidity 仅为审计教学示例,不编译部署、不执行、不针对任何真实合约。
