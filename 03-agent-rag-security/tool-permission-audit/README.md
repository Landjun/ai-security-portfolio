# 工具:Agent 工具调用权限审计 (Tool-Call Permission Audit)

> `03` 核心模块第二个工具。用纯 Python(零依赖、无需 API Key)演示 AI Agent 的"过度授权"风险,并实现一个最小权限审计器,在工具真正执行前对每次调用做放行/确认/拒绝判定。
> 对应 OWASP LLM Top 10:**LLM06: 过度授权 (Excessive Agency)**。

## 与第一个工具的关系

| 工具 | 守的是什么 |
|------|-----------|
| [RAG 注入检测器](../rag-injection-detector/) | 进入模型的**数据**(别让投毒文档劫持模型) |
| **本工具:工具调用审计** | Agent 能执行的**动作**(就算被劫持,也别让它干坏事) |

> 纵深防御:输入端防注入,执行端控权限。两者结合才完整。

## 1. 原理

AI Agent 的价值在于能调用工具去"做事":查订单、发邮件、转账、删库……
但这也是最大风险点 —— 如果 Agent 被提示注入或越狱劫持,它可能调用高危工具
造成**真实且不可逆**的损害(转账、删数据)。这比单纯"聊天泄密"严重得多。

OWASP 把它归为 **LLM06 过度授权 (Excessive Agency)**:Agent 拥有了
超出必要的功能、权限或自主性。防御核心是**最小权限**。

## 2. 复现环境

```
tool-permission-audit/
├── tools.py     # 模拟工具注册表(读单/发邮件/转账/删库),带风险等级
├── policy.py    # 权限策略(放行/需确认/拒绝 + 参数约束)
├── auditor.py   # 审计器核心(可独立自测)
├── demo.py      # 天真执行器 vs 带审计执行器
└── README.md
```

> ⚠️ 安全边界:所有工具均为模拟实现,只返回字符串,不执行任何真实操作。

## 3. 防护方案(最小权限四要素)

1. **白名单默认拒绝**(本工具实现):不在策略表里的工具一律拒绝。
2. **分级授权**:只读放行;对外/资金动作需人工确认;数据销毁直接禁止。
3. **参数约束**:即使工具允许,参数也要在边界内(如转账金额上限),越界即拒。
4. **人审高危**:敏感动作挂起,等人工确认后才执行(Human-in-the-loop)。

补充:全程**审计日志**(谁、调了什么、决策与原因),便于事后追溯。

## 4. 修复建议

- 给 Agent 配的工具**按需最小化**,不要默认给全量权限。
- 高危工具(资金、删除、对外发送)一律走人工确认或二次校验。
- 对工具参数做强约束(白名单、上限、路径限制)。
- 把审计器做成**统一关卡**,所有工具调用必须经过它,不能绕过。
- 记录完整审计日志,定期复盘异常调用。

## 5. 检测清单

- [ ] 是否存在未在白名单中的工具被调用?
- [ ] 是否有高危工具(转账/删除)被调用?是否经过人工确认?
- [ ] 工具参数是否越界(金额超限、路径越权)?
- [ ] 单轮内是否出现异常的工具调用序列(疑似被劫持)?
- [ ] 审计日志是否完整、可追溯?

## 6. 面试表达

> "我做了一个 Agent 工具调用权限审计器,针对 OWASP LLM06 过度授权:模拟一个被劫持的 Agent 想依次转账、删库、跑任意 shell,天真执行器会全部照做造成灾难;我的审计器在每次工具执行前按最小权限判定——白名单默认拒绝、只读放行、资金/对外动作挂起人工确认、参数越界(如转账超限)直接拦截。我能讲清为什么 Agent 安全的重点从'说什么'转移到了'能做什么',以及最小权限、参数约束、人审高危、审计日志这套工程化防护。"
