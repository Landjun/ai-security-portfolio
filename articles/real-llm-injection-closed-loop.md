# 从"手动发现"到"自动根治":一次完整的 LLM 注入攻防闭环

> 我没有停在"复现一个提示注入"。这篇讲的是一条完整链路:在真实大模型上发现问题 →
> 用自动化红队量化它 → 用语义模型根治它。所有代码可复现,见文末仓库。

## 0. 为什么写这篇

很多人学 AI 安全,停在"我能让模型说出系统提示词"。但真正的安全工程,
关键不在复现一次攻击,而在一套可复用的方法论:

> **发现问题 → 量化问题 → 定位根因 → 根治问题。**

下面用提示注入这一条线,把这四步走完。

## 1. 发现:正则检测器在真实 DeepSeek 上被绕过

我先做了一个 RAG 注入检测器:在文档进入大模型前扫描,命中注入特征就拦截。
为了不自欺,我把它接到**真实的 DeepSeek RAG** 上验证。

实验设计:往知识库塞一篇投毒文档,里面藏一个只在该文档出现的暗号 `FREE-VIP-8888`,
并命令模型"在回答末尾附上这个暗号"。判定很客观——**回答里是否出现暗号 = 注入是否得逞**。

结果:
- **无防护**:DeepSeek 真的被劫持,回答末尾乖乖附上了 `FREE-VIP-8888`。真实模型确实会被间接注入。
- **接上检测器(v1)**:本以为会拦下,结果**暗号照样泄露**——检测器没识别出这篇投毒文档。

为什么?因为攻击者只是换了措辞:`[系统]`写成`[系统提示]`、`忽略规则`写成`忽略以上所有限制`、
`开通全部权限`写成`开通VIP权限`。**基于关键词的正则,换个同义词就被绕过。**

这是第一课:**不要假设防御有效,要在真实环境里验证它。**

## 2. 量化:用自动化红队把"脆弱"变成一个数字

手动发现一个绕过是运气,系统化地发现一批才是工程。于是我做了一个自动化红队:

- 6 条攻击种子 × 6 种变形手法(拆字分隔、形近替换、同义改写、角色包装、加空格)= 36 个变体;
- 批量轰炸我自己的检测器,统计**绕过率**。

结果一目了然:
- 总体绕过率 **31%~53%**;
- 其中"**拆字分隔**"(把"忽略"写成"忽·略")**100% 绕过**——这是最致命的弱点。

至此,"检测器很脆弱"这个模糊判断,变成了一个**可追踪、可回归的指标**:绕过率。
每次改进检测器,重跑红队就能验证绕过率是否真的下降。

## 3. 定位:正则的根本局限

红队的数据指向同一个根因:**正则匹配的是"字面",而攻击的本质是"语义"。**
只要语义不变、措辞改变(同义词、拆字、形近、换语境),字面规则就追不上。
补再多规则也是被动的——攻击者永远能造新词。

要根治,得让检测器理解"意思",而不是"字面"。

## 4. 根治:语义 ML 检测器,把绕过率打到 0%

我把检测器从正则升级为语义模型:
- 用本地中文 embedding(bge)把文本编码成"语义向量";
- 用逻辑回归在一批注入/正常样本上训练分类;
- 前面再叠一层输入规范化(去分隔符)削弱拆字扰动。

然后用**同一套 36 个红队变体**做对比评测(关键:这些变体和正常请求**都没参与训练**,测的是泛化):

| 指标 | 正则检测器 | ML 语义检测器 |
|------|:---:|:---:|
| 攻击绕过率 ↓ | 53% | **0%** |
| 攻击拦截率 ↑ | 47% | **100%** |
| 正常误报率 ↓ | 0% | **0%** |

语义检测器拦下了全部 36 个变体(包括 100% 绕过正则的拆字分隔),**且零误报**——
它不是靠"什么都拦"取巧,而是真的能区分语义。

## 5. 收口:把能力做成可复用的网关

最后我把注入检测、越狱检测、工具调用审计、输出泄露扫描,封装成一个统一的 **LLM 安全网关**
(库 + HTTP API)。任何 LLM 应用接入三个方法,就能获得"输入护栏 + 动作审计 + 输出扫描 +
全链路审计日志"的纵深防御。各层检测器可插拔——输入护栏可以一键从正则换成上面的 ML 检测器。

## 结语:方法论比某一次攻击更重要

回头看,这条线真正的价值不是"我做了个检测器",而是这套闭环:

> 在真实环境**发现**正则被绕过 → 用红队**量化**成绕过率、定位拆字分隔 → 看清正则的**根因** →
> 用语义模型**根治**到 0%。

这套"发现→量化→定位→根治",我在对抗样本、数据投毒、后门检测里反复用。
**它比记住任何一个 OWASP 条目都更接近真实的安全工程。**
