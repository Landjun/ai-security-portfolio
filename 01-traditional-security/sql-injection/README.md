# 案例:SQL 注入 (SQL Injection)

> `01 传统安全` 经典案例。本地 sqlite3 靶场,演示登录绕过与参数化防御。对应 OWASP Top 10 A03:Injection。

## 1. 原理

应用把用户输入**直接拼接**进 SQL 语句时,攻击者可注入改变语句结构的内容,
绕过认证、读取或篡改数据。例如用户名输入 `admin' --`,拼出的语句变成:
```sql
SELECT role FROM users WHERE username='admin' --' AND password='...'
```
`--` 把密码校验注释掉,于是无需密码即可以 admin 登录。

## 2. 复现环境

纯本地、内存 sqlite3,无害。
```
sql-injection/
├── demo.py    # 不安全(拼接) vs 安全(参数化)对比
└── README.md
```

## 3. 防护方案

1. **参数化查询 / 预编译语句**(首选):输入只当数据,永不当代码。
2. **最小权限**:数据库账号按需授权,降低被注入后的损失。
3. **输入校验 + 白名单**:对类型/格式做校验(辅助手段,不能替代参数化)。
4. **ORM**:用成熟 ORM 默认参数化。
5. **WAF + 报错收敛**:拦截可疑载荷,不向用户暴露 SQL 报错细节。

## 4. 修复建议

- 把所有字符串拼接的 SQL 改为参数化(`?` / 占位符 + 参数元组)。
- 审查动态拼接表名/列名的场景,用白名单映射而非直接拼接。
- 关闭生产环境详细 SQL 报错。

## 5. 检测清单

- [ ] 代码里是否存在字符串拼接/格式化构造 SQL?
- [ ] 输入点(登录、搜索、排序参数)是否都参数化?
- [ ] 数据库账号是否最小权限?
- [ ] 报错是否泄露 SQL 结构?
- [ ] 是否有 SQLi 自动化扫描纳入测试?

## 6. 面试表达

> "我用本地 sqlite3 复现了 SQL 注入:不安全的登录把用户名密码直接拼进 SQL,我输入 `admin' --` 就把密码校验注释掉、无需密码以管理员登录;改成参数化查询后,同样的载荷只被当作普通字符串,注入失败。我能讲清注入的本质是'数据被当成代码执行',以及参数化查询、最小权限、白名单校验这套防御,对应 OWASP A03。"

## 运行 & 验证

```powershell
cd 01-traditional-security\sql-injection
python demo.py
```
预期:不安全版被 `admin' --` 绕过登录;安全版注入失败。
